# Phoenix Procurement - Internal Deployment & Hardening Runbook

**Audience:** IT / infrastructure team deploying Phoenix Procurement on the internal local/private server.
**Current production posture:** no Firebase by default. The production package is staged for the SQL/API backend with `demoMode: false`, `authMode: 'internal'`, and `dataMode: 'api'`.

This runbook is intentionally conservative: the app can be tested in a closed environment with the current internal operator setup, but pilot/go-live still needs IT-owned server-side identity, authorization, TLS, backups, and service-account handling.

## 0. What This Deliverable Is

The project ships two full-snapshot packages only:

- `Phoenix Procurement DEMO FULL.zip` - Firebase/demo mode for prototype testing.
- `Phoenix Procurement PRODUCTION FULL.zip` - internal SQL/API mode for local/private server testing.

The production package contains:

- the production HTML build under `dist/phoenix-procurement-PRODUCTION.html`;
- browser source, docs, tools, and backend source;
- no `node_modules`, backend `dist`, `.git`, `local.settings.json`, or secret/key files.

## 1. Production App Mode

The production package generated by `tools/package.py` sets:

```js
demoMode: false
authMode: 'internal'
dataMode: 'api'
apiBaseUrl: '/api'
```

In this mode:

- Firebase modules are not loaded.
- The browser reads its working data from `GET /api/records`.
- Normal business writes still go through `PXStore`, then `PXApiClient`, then the backend `/api/records` routes.
- Demo role switching and URL role overrides are disabled by `demoMode: false`.

Do not change the production package back to Firebase/password unless IT explicitly approves that path.

## 2. Backend Runtime

The backend is under `backend/` and uses Azure Functions v4, Node/TypeScript, and SQL Server through `mssql`.

Required app settings:

- `FUNCTIONS_WORKER_RUNTIME=node`
- `SQL_CONNECTION_STRING=<IT-approved SQL Server connection string>`
- `AzureWebJobsStorage=<real Azure Storage, Azurite, or approved Functions storage setting>`
- `ORDER_ALERTS_ENABLED=false` until Graph notification settings are ready
- Graph settings only when notifications are enabled:
  - `GRAPH_TENANT_ID`
  - `GRAPH_CLIENT_ID`
  - `GRAPH_CLIENT_SECRET`
  - `GRAPH_MAIL_SENDER_USER_ID`

Important local note: timer triggers need `AzureWebJobsStorage`. HTTP endpoints can build and test without Graph credentials, but the Functions host will complain about timer listeners if storage is missing or unreachable.

## 3. SQL Server Setup

Run the backend migrations against the approved SQL database:

```powershell
cd backend
pnpm install
$env:SQL_CONNECTION_STRING='<connection string>'
pnpm run db:migrate
```

Current migrations create:

- `dbo.orders`
- `dbo.sync_exceptions`
- `dbo.import_audit`
- `dbo.notification_state`
- `dbo.operational_records`
- `dbo.app_counters`

Current migrations also add read/support indexes through
`backend/db/006_order_merge_indexes.sql`, including the merged order read/head
path used by the API-mode browser.

Use least-privilege SQL principals:

- write principal for sync and operational record routes;
- read-only principal for BI/read-only endpoints if IT separates connection pools later.

For local development only, `TrustServerCertificate=True` is acceptable. Production should use trusted certificates and the final IT-approved encryption settings.

## 4. Backend Health and Smoke Test

Start the backend:

```powershell
cd backend
$env:FUNCTIONS_WORKER_RUNTIME='node'
$env:SQL_CONNECTION_STRING='<connection string>'
pnpm start
```

Check:

```powershell
Invoke-RestMethod http://localhost:7071/api/health
Invoke-RestMethod -Headers @{ "x-functions-key" = "<function-key>" } http://localhost:7071/api/records
Invoke-RestMethod -Method Post -Headers @{ "x-functions-key" = "<function-key>" } http://localhost:7071/api/counters/smoke:counter/next
```

Expected:

- `/api/health` returns SQL healthy.
- `/api/records` returns a grouped payload with the allowed business collections.
- `/api/counters/.../next` returns an incrementing value. This is used for API-mode generated references such as RFP numbers.

## 5. Static App Hosting

Host `dist/phoenix-procurement-PRODUCTION.html` over HTTPS on the approved internal server.

Recommended setup:

- same origin for static HTML and backend API so `apiBaseUrl: '/api'` works unchanged;
- HTTPS certificate trusted by company workstations;
- network access restricted to the internal/VPN environment;
- no real function keys or secrets committed into source or package files.

If the backend is on a different internal URL, IT may edit `APP_CONFIG.apiBaseUrl` and `APP_CONFIG.apiFunctionKey` in the deployed production file or a controlled deployment transform. Do not commit real keys.

## 6. Identity and Authorization

The current `authMode: 'internal'` local operator setup identifies a workstation session and assigns the configured default role. This is acceptable for closed-environment testing only.

Before pilot/go-live, IT must choose and enforce one server-side identity path:

- Entra ID / Microsoft 365 SSO;
- Windows-integrated/IIS authentication;
- APIM or reverse-proxy policy that injects verified user identity;
- Firebase password/SSO only if IT deliberately reselects Firebase.

The backend operational-record API re-enforces the browser write permission matrix against the stored officer role and rejects invalid high-risk payloads. Browser checks are still not sufficient for production: IT must ensure the gateway/backend identity policy makes the submitted user identity trustworthy and impossible to spoof.

## 7. Data Preparation

Before business pilot:

- seed officers/roles or identity mappings;
- seed suppliers, working calendars, import rules, and entity-specific reference data;
- import representative Phoenix, Seychelles Breweries, and Edena ERP data through the approved manual import or backend sync feed;
- run KPI backfill if historical trend reporting is required;
- take a SQL backup before opening the app to users.

The real Data Warehouse feed is not connected yet. Until IT provides the final warehouse view/API, Excel import and fixture-backed backend sync remain controlled test feeds.

## 8. Pre-Pilot Checklist

- [ ] Only the two approved package zips exist in the project root.
- [ ] `python build.py` passes.
- [ ] `backend pnpm test` passes; SQL integration passes where SQL Server is available.
- [ ] `backend pnpm test` with `RUN_SQL_INTEGRATION=true` passes against the target-like SQL test database, including the sync-to-records E2E flow.
- [ ] SQL migrations have been applied to the target database.
- [ ] `/api/health` returns SQL healthy.
- [ ] `/api/records` returns a grouped payload.
- [ ] Production HTML has `demoMode: false`, `authMode: 'internal'`, and `dataMode: 'api'`.
- [ ] Function keys, SQL passwords, Graph secrets, and service-account keys are stored only in server/app settings or Key Vault.
- [ ] HTTPS and internal network restrictions are in place.
- [ ] Identity and server-side authorization approach is signed off for pilot risk level.
- [ ] Backup/restore procedure is documented and tested.

## 9. If IT Reselects Firebase

Firebase is no longer the default production path. If IT deliberately reselects it, the team must update this runbook and production package settings, then:

- create a dedicated production Firebase project;
- deploy and test Firestore security rules;
- restrict Firebase API keys;
- configure individual user authentication;
- run role-by-role access testing.

Do not mix the two production paths casually. Choose one deployment architecture and keep the docs, package settings, and security model aligned.
